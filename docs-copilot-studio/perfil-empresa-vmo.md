## 2. O QUE É O VMO (Value Management Office)

O VMO é a evolução do PMO tradicional. Enquanto o PMO foca em **controle e processos**, o VMO foca em **geração de valor para o negócio**.

### PMO vs VMO

| Dimensão | PMO Tradicional | VMO (Value Management Office) |
|----------|----------------|-------------------------------|
| Foco | Controle de projetos | Geração de valor |
| Métricas | Prazo, custo, escopo | Valor entregue, ROI, benefícios realizados |
| Postura | Fiscalizador | Parceiro estratégico |
| Visão | Projeto a projeto | Portfólio e estratégia |
| Relatórios | Status de cronograma | Impacto no negócio |
| Decisões | Operacionais | Estratégicas |
| Sponsor | Gerente de projeto | C-Level / Diretoria |

### Por que o VMO importa
- Projetos de TI frequentemente falham por falta de alinhamento com o negócio, não por problemas técnicos
- O VMO garante que cada projeto tenha **justificativa de valor clara** antes de consumir recursos
- Governança desde a demanda evita projetos "fantasmas" que chegam na TI sem aprovações reais

## 4. METODOLOGIA VMO — PRINCÍPIOS

### 4.1 Ciclo de Vida de um Projeto VMO

Todo projeto passa obrigatoriamente por **5 fases**:

```
01-QUALIFICAÇÃO → 02-INICIAÇÃO → 03-PLANEJAMENTO → 04-MONITORAMENTO → 05-ENCERRAMENTO
```

**01 - Qualificação**
- Coleta estruturada da demanda (Iara Inbound)
- Gate de intake — verificação de aprovações (Gabriel)
- Sizing inicial de esforço e complexidade (Rafael)
- Score de qualificação 0-30 (Felipe)
- Gate de qualificação — decisão de avançar ou reprovar (Gabriel)

**02 - Iniciação**
- Termo de Abertura do Projeto (TAP)
- PM Canvas (9 blocos)
- Plano Geral do Projeto

**03 - Planejamento**
- Especificação de Requisitos (ERF: RFs + RNFs com MoSCoW)
- Work Request / mini-RFP para fornecedores
- Cronograma e WBS
- Plano de Riscos
- Framework de KPIs e EVM

**04 - Monitoramento**
- Status Reports periódicos
- Controle de mudanças de escopo
- Atualização de riscos e indicadores

**05 - Encerramento**
- Revisão de qualidade do pacote completo (Vera)
- Auditoria de governança (Gabriel)
- Aprovação formal e encerramento

### 4.2 Gates de Qualidade (Go/No-Go)

A VMO opera com **gates obrigatórios** — pontos de decisão onde o projeto só avança se critérios mínimos forem atendidos:

| Gate | Momento | Critério Mínimo |
|------|---------|----------------|
| **Gate 1 — Intake** | Antes de qualquer análise | Aprovações documentadas presentes |
| **Gate 2 — Qualificação** | Após score Felipe | Score ≥ 15/30 |
| **Gate 3 — Iniciação** | Após documentação base | Sponsor designado, TAP completo |
| **Gate 4 — Planejamento** | Após todos os documentos | Score Vera ≥ 70/100 |
| **Gate Final** | Antes de aprovação | Sem NC-CRÍTICAs abertas |

### 4.3 Código de Projetos

Todo projeto recebe um código no formato: `PROJ-AAAA-NNN`

- `PROJ` — prefixo fixo
- `AAAA` — ano de abertura (ex: 2026)
- `NNN` — número sequencial com zero à esquerda (ex: 007)

Exemplos: `PROJ-2026-001`, `PROJ-2026-007`, `PROJ-2026-012`

## 5. TOM DE VOZ E COMUNICAÇÃO

### 5.1 Princípios de Comunicação VMO
- **Profissional e estratégico:** Linguagem de C-Level, orientada a resultados
- **Direto e objetivo:** Sem floreios ou jargão desnecessário
- **Consultivo:** Apresenta alternativas, não apenas problemas
- **Baseado em evidências:** Toda afirmação tem dado ou referência

### 5.2 Vocabulário Preferido

| ✅ USE | ❌ EVITE |
|-------|---------|
| "gerar valor" | "fazer o projeto" |
| "benefícios mensuráveis" | "melhorias esperadas" |
| "critérios de sucesso" | "o que esperamos" |
| "sponsor executivo" | "patrocinador" |
| "gate de qualidade" | "ponto de controle" |
| "rastreabilidade" | "ligação entre documentos" |
| "Work Request" | "pedido de proposta informal" |
| "NC-CRÍTICA" | "problema grave" |
| "baseline de prazo/custo" | "estimativa inicial" |
| "EVM" | "controle de custos" |
| "roadmap do portfólio" | "lista de projetos" |

### 5.3 Estrutura de Documentos
Todos os documentos VMO seguem o padrão:
- Cabeçalho com: código do projeto, título, data, versão, autor (agente)
- Seções numeradas
- Tabelas para dados estruturados (nunca listas quando tabela é mais claro)
- Conclusões/recomendações ao final
- Sem emojis em documentos formais (só em interfaces de chat/status)

## 7. REGRAS DE NEGÓCIO CONSOLIDADAS

Estas regras foram aprendidas ao longo das execuções do VMO Squad e são **obrigatórias**:

### RN-01 — Dupla Aprovação Obrigatória
Nenhuma demanda avança sem aprovação **documentada** de:
1. Diretoria da área solicitante (cargo ≥ Gerente Sênior)
2. Gerente de TI ou superior

### RN-02 — Evidência para Urgência Alta
Urgência declarada > 3/10 exige documento probatório. Sem evidência, urgência = 3/10. Felipe não pode usar urgência inflada no score.

### RN-03 — Rafael Antes de Felipe
O sizing do Rafael é pré-requisito para o critério 7 de Felipe (Esforço). Sequência obrigatória: **Step de Sizing → Step de Qualificação**.

### RN-04 — InterCompany Mesma Divisão
Projetos de integração entre sistemas da mesma divisão organizacional são considerados **mesma área operacional** para fins de complexidade e governança.

### RN-05 — GMUD não define tipo de projeto
A existência de uma GMUD (Gestão de Mudança) no processo não diferencia automaticamente um projeto de melhoria de um projeto novo. A classificação deve ser feita por Rafael com base no escopo real.

### RN-06 — Score Vera Mínimo 70
Pacote de documentos com score Vera < 70 **volta para Diana** (documentação base). O loop pode ocorrer no máximo **2 vezes**. Na 3ª reprovação, escalar para o usuário.

### RN-07 — Sponsor Antes do Planejamento
O sponsor executivo deve ser confirmado **antes** de Diana criar o TAP. Sponsor indefinido = campo "A CONFIRMAR" no TAP + NC-MENOR no Gate de Qualificação.
